### `resolved_by` — read this one

Every confirmed edge records how it got confirmed:

- `direct_extraction` — unambiguous on the first pass
- `retry:kg_precedent` / `retry:widen_context` / `retry:alternate_parse` — the agent
  resolved an ambiguity itself instead of escalating
- `human` — a reviewer confirmed it

§4.2 requires human-confirmed facts never be indistinguishable from AI-generated ones.
This field is that guarantee. In the sample document 3 of 4 ambiguities are resolved by
the retry loop and only 1 reaches the queue.

### For Dev 1 specifically

`escalation.sample.json` matches the `EscalationRecord` block in `WORK-SPLIT.md`, plus an
`id` and a `target_edge_id`. **Import the model from `backend/app/schemas.py` rather than
re-declaring the enums** — a `pending` vs `pending_review` mismatch splits the queue
silently.

`trace` is what distinguishes "nobody has looked at this yet" from "the agent already
tried three things". `rounds_attempted: 0` would mean escalated without any retry;
anything higher means the strategies in `trace` were tried and failed, in order, and each
`result` is written to be readable by a human.

## Redline Generator fixtures

Generated by `python -m app.redline.pipeline --publish`, and pinned by
`tests/test_redline_fixtures.py` the same way the Clause NER ones are.

### `redline.sample.json` and `escalation.redline.json` - output

`redline.sample.json` was hand-written while the stage did not exist. It is generated
now, from a real run. Two things changed for Dev 1 when it became real:

- **A redline has a `status`.** `GET /documents/{id}/redlines` serves `confirmed` only by
  default. A `pending_review` redline is one the loop grounded but was not confident
  enough to stand behind; it is in the queue waiting for a human, and the dashboard must
  not show it as a suggestion. Pass `?status=pending_review` to see it deliberately.
- **`grounding_chunk_ids` / `grounding_edge_ids` name the evidence.** Every redline can
  be traced to the clauses and confirmed edges it was written from.

`trace` is still `TraceRound` verbatim, so `TraceTimeline` renders a retrieval trace and a
Clause NER retry trace with no branching. `escalation.redline.json` matches
`EscalationRecord` plus `id` and `target_redline_id` - the latter is what makes approving
a queue item flip the redline itself. It is `null` on the `budget_exhausted` items,
because ARCHITECTURE.md 4.1 forbids writing a redline the agent could not ground: there
is nothing to point at, on purpose.

### `risk.sample.json` and `playbook.sample.json` - proposed input contract, Dev 4 please confirm

Same deal as `chunks.sample.json` was with Dev 2: hand-written, published early so the
Redline Generator was not blocked, and wrong is fine as long as you say so.

They follow the `risk_flags` and `playbook_rules` shapes in `schema.sql` rather than
inventing a new one, joined on `(rule_id, rule_version)`. What this stage actually needs
from you:

| Field | Why |
|---|---|
| `status` | `flagged` triggers a redline; `suppressed` does not. A suppressed flag was already cleared against a confirmed edge and redlining it would undo that |
| `rule_id` + `rule_version` | the redline is justified against the rule that *fired*, not the active version |
| `triggering_fact_ids` | seeds retrieval - the loop should not have to search for facts you already had |
| `clause_ref` | the join key, as everywhere else |
| `standard_language` (playbook) | what the rewrite aims at. Without it a redline is a model's opinion rather than a versioned rule |

**Two open items, both bigger than this file:**

1. `schema.sql` types `document_id` as `uuid`; every Dev 2/3 model and fixture uses text
   (`"DOC-001"`). The fixtures here stay text so the stage runs against Dev 3's real
   output. The two sides have to converge before they share a database.
2. `risk.sample.json` **changed shape** when it moved to the `schema.sql` columns. It lost
   `title`, `rationale` and `triggers_redline`. `rationale` now lives on the playbook rule
   and is joined by `rule_id`; `triggers_redline` is `status == "flagged"`. Dev 1: the
   `/documents/{id}/risk-flags` stub route serves the new shape.
